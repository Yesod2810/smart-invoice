## 1. Project Overview

Smart Invoice is a web-based invoice management system designed to automate invoice creation, financial calculations, PDF generation, email delivery, and payment tracking.

The system provides a centralized platform where business administrators and staff can manage customers, products, invoices, and payment records.

The backend will be developed using Java and Spring Boot, with PostgreSQL as the relational database and Docker for containerized deployment.

The initial release focuses on delivering a functional REST API backend. A web-based dashboard may be developed in a later phase.

## 2. Problem Statement

Traditional invoice management processes often rely on Microsoft Excel, Word, or manual data entry.

These processes introduce several operational problems:

- Manual calculations may result in incorrect invoice totals.
- Customer information may be duplicated or inconsistent.
- Invoice documents require repetitive manual preparation.
- Employees may forget to send invoices or follow up on overdue payments.
- Payment records may not be synchronized with invoice information.
- Searching and managing historical invoices can become difficult as transaction volume increases.
- Manual workflows make auditing and reporting more complicated.

Smart Invoice aims to reduce repetitive operations and improve the consistency, accuracy, and traceability of invoice management.

## 3. Project Objectives

The main objective is to develop a secure and maintainable backend system that supports automated invoice processing.

Specific objectives include:

### OBJ-01 — Centralized Data Management

Provide a centralized database for customers, products, invoices, and payment records.

### OBJ-02 — Automated Invoice Calculation

Automatically calculate invoice subtotals, discounts, applicable taxes, and final payable amounts.

### OBJ-03 — PDF Generation

Generate downloadable PDF documents from stored invoice information.

### OBJ-04 — Automated Email Delivery

Allow staff to send invoices to customers through email without manually preparing attachments.

### OBJ-05 — Payment Tracking

Support full and partial payment recording and maintain outstanding balances.

### OBJ-06 — Security and Access Control

Protect business information through authentication and role-based authorization.

### OBJ-07 — Deployment and Maintainability

Package the application using Docker and provide documentation for installation, development, testing, and deployment.

## 4. Target Users and Stakeholders

### 4.1 Administrator

The Administrator is responsible for managing system access, business information, and operational activities.

Responsibilities:

- Manage staff accounts.
- Configure business information.
- Access customer and product records.
- View and manage invoices.
- Review payment information.
- Access operational and audit information.

### 4.2 Staff

Staff members are responsible for daily invoice operations.

Responsibilities:

- Create and update customer information.
- Manage products and services.
- Create invoice drafts.
- Review and issue invoices.
- Generate PDF documents.
- Send invoices to customers.
- Record customer payments.
- Search and review existing invoices.

Staff permissions must be limited according to the configured authorization rules.

### 4.3 Customer

Customers are the recipients of invoices generated by the system.

In the initial MVP, customers do not require system accounts.

Customers receive invoices through email and can access the information provided in the invoice document.

A dedicated customer portal may be introduced in a future release.

## 5. Project Scope

### 5.1 In Scope — MVP

The following features are included in the initial release.

#### FR-01 — Authentication and Authorization

- User login.
- Secure password storage.
- Role-based authorization.
- Administrator and Staff roles.
- Protection of restricted API endpoints.

#### FR-02 — Customer Management

- Create customer records.
- Retrieve customer information.
- Update customer information.
- Search and list customers.
- Validate customer data.

Customer information includes name, email, phone number, address, and optional tax identification information.

#### FR-03 — Product Management

- Create products and services.
- Update product information.
- Retrieve product information.
- Search and list products.
- Store SKU, name, unit price, unit of measurement, and tax configuration.

#### FR-04 — Invoice Management

- Create invoice drafts.
- Add multiple invoice items.
- Retrieve invoice details.
- Update draft invoices.
- Calculate invoice totals automatically.
- Issue invoices.
- Search and filter invoices.
- Manage invoice lifecycle states.

Financial information on issued invoices must remain historically consistent.

#### FR-05 — Invoice PDF Generation

- Generate PDF documents from invoice data.
- Display business information.
- Display customer information.
- Display itemized invoice details.
- Display subtotal, discounts, taxes, and final amount.
- Support Vietnamese text and currency formatting.
- Allow authorized users to download PDF documents.

#### FR-06 — Email Delivery

- Send invoices to customers through email.
- Attach generated PDF documents.
- Record email delivery attempts.
- Handle email delivery failures.
- Support retrying failed delivery attempts.

#### FR-07 — Payment Management

- Record customer payments.
- Support partial payments.
- Calculate outstanding balances.
- Maintain payment history.
- Identify fully paid and unpaid invoices.

#### FR-08 — API Documentation

- Provide RESTful API endpoints.
- Document request and response structures.
- Document validation rules.
- Provide OpenAPI/Swagger documentation.

#### FR-09 — Containerized Deployment

- Package the backend application using Docker.
- Run PostgreSQL using Docker.
- Configure services through Docker Compose.
- Manage environment-specific configurations.
- Persist database data using Docker volumes.

### 5.2 Should Have — Secondary Features

These features will be implemented after the core invoice workflow is stable, subject to available development time.

- Scheduled invoice creation.
- Automatic overdue payment reminders.
- Revenue summary reports.
- Advanced invoice filtering.
- Audit logging (the `audit_logs` table and issuance/payment events are built with the MVP schema; the audit query API is P1 — see US-13).
- Email notification templates.
- Basic system monitoring.

### 5.3 Out of Scope — Initial MVP

The following features are excluded from the initial release:

- Full frontend dashboard.
- Native Android or iOS application.
- Online payment gateway integration.
- Multi-tenant SaaS architecture.
- Automated accounting and tax declaration.
- Inventory and warehouse management.
- AI-based invoice recognition.
- Advanced financial analytics.
- Digital signature integration.
- Official electronic tax-invoice provider integration.

These features may be implemented in subsequent development phases.

The initial PDF invoice functionality must not be represented as a legally valid electronic tax invoice unless the applicable regulatory requirements and integrations have been implemented and verified.

## 6. Core Business Workflow

The primary invoice workflow is defined as follows:

### Step 1 — Authentication

An authorized employee logs in to the system.

### Step 2 — Customer Selection

The employee selects an existing customer or creates a new customer record.

### Step 3 — Product Selection

The employee selects products or services and specifies their quantities.

### Step 4 — Invoice Calculation

The backend retrieves product prices and calculates invoice amounts.

### Step 5 — Draft Creation

The invoice is stored in PostgreSQL with a DRAFT status.

### Step 6 — Invoice Review and Issuance

The employee reviews the invoice and confirms issuance.

The system assigns an invoice number and preserves the issued financial information.

### Step 7 — PDF Generation

The system generates a PDF using the stored invoice information.

### Step 8 — Email Delivery

The invoice document is sent to the customer's email address.

### Step 9 — Payment Recording

The employee records payments against the invoice.

### Step 10 — Invoice Completion

The system updates the outstanding balance and payment status.

The invoice payment status becomes PAID when its outstanding balance becomes zero. The invoice lifecycle status remains ISSUED (lifecycle and payment status are tracked separately — see 03-BUSINESS-RULES.md §8).

## 7. Non-Functional Requirements

### NFR-01 — Security

- Passwords must be securely hashed.
- Sensitive API endpoints must require authentication.
- Role-based authorization must be enforced.
- Secrets must not be committed to Git.
- Production communication must use HTTPS.

### NFR-02 — Data Integrity

- Financial values must use decimal-safe data types.
- Database constraints must protect relational integrity.
- Business transactions must be atomic.
- Duplicate invoice issuance must be prevented.
- Historical invoice information must be preserved.

### NFR-03 — Reliability

- Failed database transactions must be rolled back.
- Email delivery failures must not invalidate successfully issued invoices.
- Background operations must support safe retry mechanisms.
- Important operations must be traceable through logs.

### NFR-04 — Maintainability

- The backend must follow modular architecture.
- Business logic must be separated from HTTP controllers.
- Database schema changes must use versioned migrations.
- Important modules must have automated tests.
- API contracts must be documented.

### NFR-05 — Deployment

- The system must support Docker-based deployment.
- Configuration must be externalized using environment variables.
- Database data must persist across container restarts.
- Database backup and restoration procedures must be documented.

## 8. Technical Architecture

The initial system will use Modular Monolith Architecture.

The backend will be implemented as one Spring Boot application divided into independent business modules.

Technology stack:

## 9. Project Constraints

The initial implementation must satisfy the following constraints:

- The project is developed primarily as a backend application.
- The development period is planned for 30 days.
- The primary programming language is Java.
- PostgreSQL is the primary relational database.
- Docker is required for application deployment.
- The project will initially support a single business organization.
- External payment gateway integration is excluded.
- Full legal electronic tax-invoice integration is excluded.
- The MVP will prioritize functional correctness over advanced UI features.

## 10. Assumptions and Dependencies

The project assumes that:

- Developers have access to Java, Docker, and Git.
- Customers have valid email addresses.
- Product and pricing information is maintained by authorized employees.
- The application can access a configured SMTP service.
- The deployment environment supports Docker containers.
- Tax configuration is supplied according to the applicable business rules.
- A PostgreSQL database is available for application storage.

## 11. Project Risks

| Risk | Potential Impact | Mitigation |
| --- | --- | --- |
| Incorrect invoice calculations | Financial data inconsistency | Unit tests and BigDecimal |
| Duplicate invoice issuance | Duplicate invoice numbers | Database constraints and transaction controls |
| Email delivery failure | Customer does not receive invoice | Retry mechanism and delivery logs |
| Database failure | Service interruption or data loss | Persistent storage and backups |
| Unauthorized API access | Sensitive business data exposure | Authentication and authorization |
| Scope expansion | Project delays | Prioritize MVP requirements |
| Incorrect tax configuration | Incorrect calculated tax | Configurable tax rules and validation |

## 12. Acceptance Criteria

The MVP will be considered functionally complete when:

- Authorized users can log in successfully.
- Customer and product APIs support the required CRUD operations.
- Staff can create an invoice with multiple items.
- Invoice calculations produce accurate results.
- The system stores invoices in PostgreSQL.
- Staff can issue an invoice and retrieve its PDF.
- The system can send invoice emails.
- Full and partial payments can be recorded.
- Unauthorized users cannot access restricted endpoints.
- Automated tests cover critical business operations.
- The application can run through Docker Compose.
- API documentation is available.
- Core workflows have passed end-to-end testing.

## 13. Definition of Done

A feature is considered complete when:

1. The implementation satisfies its acceptance criteria.
2. The code compiles successfully.
3. Relevant unit tests pass.
4. Relevant integration tests pass.
5. Validation and error handling are implemented.
6. Database migrations are included when required.
7. API documentation is updated.
8. The implementation is committed to Git.
9. The feature has been reviewed and integrated into the development branch.
