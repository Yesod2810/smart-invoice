## 1. Document Purpose

This document defines the business rules governing the Smart Invoice system.

Business rules describe the conditions, constraints, calculations, and workflows that must be enforced to ensure that invoice operations remain accurate, consistent, secure, and traceable.

These rules must be implemented primarily in the backend rather than relying on frontend validation.

The document serves as a reference for:

- Domain model implementation.
- Business service development.
- Database constraints.
- Invoice calculation.
- Invoice lifecycle management.
- Payment processing.
- Error handling.
- Automated testing.
- API validation.

All development must comply with the rules defined in this document.

## 3. Authentication and Authorization Rules

### BR-AUTH-001 — Authentication Required

All protected API endpoints must require valid authentication credentials.

Public endpoints may include:

- Login.
- Health check endpoints that are explicitly configured as public.

All other endpoints must be protected according to their authorization requirements.

### BR-AUTH-002 — Password Security

User passwords must never be stored in plaintext.

Passwords must be stored using a secure password-hashing mechanism supported by Spring Security.

Password hashes must never appear in API responses.

### BR-AUTH-003 — Role-Based Authorization

The system supports two initial roles:

- ADMIN
- STAFF

ADMIN users can access administrative operations.

STAFF users can access permitted business operations.

Administrative actions must not be accessible to STAFF users.

### BR-AUTH-004 — Authentication Errors

Invalid or missing authentication credentials must return:

HTTP 401 Unauthorized

Authenticated users without the required permission must receive:

HTTP 403 Forbidden

### BR-AUTH-005 — Disabled Accounts

Disabled accounts must not be allowed to authenticate or access protected business operations.

## 4. Customer Management Rules

### BR-CUS-001 — Required Customer Information

A customer record must contain:

- Customer name.
- Valid email address.
- Billing information required by the business.

Phone number, tax identification number, and additional contact information may be optional according to business configuration.

### BR-CUS-002 — Email Validation

Customer email addresses must follow a valid email format.

Invalid email addresses must be rejected before persistence.

### BR-CUS-003 — Customer Identity

Each customer must have a unique internal identifier.

The primary key must be generated by the system.

Customer names and email addresses are not automatically unique because different customer records may legitimately share them.

### BR-CUS-004 — Historical Information

Updating customer information must not modify customer information stored in previously issued invoices.

Issued invoices must use historical customer snapshots.

### BR-CUS-005 — Customer Deactivation

A customer referenced by historical invoices must not be physically deleted if doing so would compromise financial records.

A customer may be deactivated instead.

Historical invoices must remain accessible.

## 5. Product Management Rules

### BR-PRO-001 — Unique Product SKU

Each product must have a unique SKU within the business catalogue.

Duplicate SKUs must be rejected.

The database must enforce this rule using a unique constraint.

### BR-PRO-002 — Valid Unit Price

Product prices must be zero or greater.

Negative prices are not permitted.

### BR-PRO-003 — Product Availability

Inactive products must not be selectable for new invoice items unless an explicitly authorized workflow permits it.

Existing invoices referencing inactive products must remain accessible.

### BR-PRO-006 — No Physical Deletion

Deleting a product through the API deactivates it.

Products are never physically deleted through ordinary business workflows.

### BR-PRO-004 — Historical Price Preservation

Changing a product price must not update the price stored in an issued invoice.

Invoice items must store the applicable price at the time of issuance.

Invoice items copy the product's price, tax rate, and descriptive fields into the item record. Whether an existing DRAFT is re-priced from the catalogue when the product changes, or keeps the values captured when the line was added, is an open decision (see 06-DAY-1-REVIEW.md, DEC-01). In either case the values are frozen at issuance.

### BR-PRO-005 — Product Snapshot

An issued invoice item must retain:

- Product SKU.
- Product name.
- Product description, where applicable.
- Unit of measurement.
- Unit price.
- Quantity.
- Discount.
- Applicable tax rate.
- Calculated line amounts.

The original product ID may remain as a reference but must not be the only source of historical invoice information.

## 6. Invoice Creation Rules

### BR-INV-001 — Valid Customer

An invoice must reference an existing customer.

An invoice creation request referencing a nonexistent customer must be rejected.

### BR-INV-002 — Minimum Invoice Items

An invoice must contain at least one item before it can be issued.

An empty invoice must not be issued.

### BR-INV-003 — Valid Quantity

Each invoice item must have a quantity greater than zero.

Quantity must use an appropriate decimal type if fractional quantities are supported.

### BR-INV-004 — Server-Side Calculation

The backend is responsible for calculating invoice amounts.

The frontend must not be treated as the authoritative source for:

- Unit prices.
- Subtotals.
- Tax amounts.
- Final invoice totals.

### BR-INV-005 — Draft Invoice

New invoices must initially be created with the status:

DRAFT

A draft may be reviewed and modified before issuance.

### BR-INV-006 — Invoice Currency

Every invoice must specify a supported currency.

The initial MVP supports VND.

Additional currencies may be introduced in future releases.

Currency precision and rounding rules must be configured explicitly.

### BR-INV-007 — Invoice Dates

An invoice may contain:

- Creation date.
- Issue date.
- Due date.

The issue date must be assigned when the invoice is issued.

The due date must not be earlier than the issue date when the invoice is issued.

### BR-INV-008 — Atomic Creation

Invoice creation and invoice-item persistence must occur within a single database transaction.

If any part of the operation fails, all changes must be rolled back.

A partially created invoice must not remain in the database.

## 7. Invoice Calculation Rules

Financial calculations are critical to the Smart Invoice system.

All calculations must be deterministic, testable, and performed using decimal-safe arithmetic.

### BR-CAL-001 — Monetary Data Types

Java must use BigDecimal for financial amounts.

PostgreSQL must use NUMERIC or DECIMAL for monetary values.

The following types must not be used for financial calculations:

- float
- double

BigDecimal values must be created using decimal strings or other exact representations rather than binary floating-point constructors.

### BR-CAL-002 — Line Amount Calculation

For each invoice item:

Line Amount = Quantity × Unit Price

Example:

Quantity = 2

Unit Price = 500,000 VND

Line Amount = 1,000,000 VND

### BR-CAL-003 — Subtotal Calculation

Invoice Subtotal = Sum of all Line Amounts

The subtotal must be calculated by the backend.

### BR-CAL-004 — Discount Validation

Discounts must be zero or greater.

A discount must not exceed the amount to which it applies.

For an invoice-level fixed discount:

Invoice Discount <= Subtotal

The MVP uses a fixed invoice-level discount amount.

Percentage discounts and combined discount policies are future extensions.

### BR-CAL-005 — Tax Calculation

Tax must be calculated using the applicable tax configuration.

The initial system must support item-level tax rates rather than assuming all products have the same rate.

For an invoice-level discount, the discount must be allocated across all invoice lines (including 0% tax lines) before tax calculation.

The allocation policy must be deterministic.

A proportional allocation based on line amounts is the default design.

The final allocation must account for rounding differences.

The applicable tax rate must be stored in each issued invoice item.

Tax rates must not be hardcoded globally.

### BR-CAL-006 — Taxable Amount

For a line item:

Taxable Amount = Line Amount - Allocated Discount

The taxable amount must not be negative.

### BR-CAL-007 — Tax Amount

For an exclusive-tax pricing model:

Tax Amount = Taxable Amount × Tax Rate

The initial MVP uses exclusive-tax pricing.

Tax-inclusive pricing may be introduced in a future version.

### BR-CAL-008 — Grand Total

The final invoice amount is:

Grand Total = Subtotal - Total Discount + Total Tax

The total must be zero or greater.

The backend must calculate all components using the same configured calculation policy.

### BR-CAL-009 — Currency Precision

The initial VND configuration uses whole-unit final monetary amounts.

Intermediate calculations may retain additional precision.

Rounding must be applied consistently according to the configured calculation policy.

The initial technical policy is:

RoundingMode.HALF_UP

This policy must be reviewed if the system is adapted for actual regulated tax-invoice processing.

### BR-CAL-010 — Calculation Consistency

The sum of item-level values must reconcile with invoice-level totals.

If rounding produces a remainder during discount allocation, the system must allocate that remainder deterministically.

The system must not silently discard financial differences.

### BR-CAL-012 — Calculation Sequence

The calculation service must apply the following fixed sequence. `round()` means rounding to the currency scale (0 for VND) with the rounding mode in BR-CAL-009.

1. `line_amount = round(quantity × unit_price)`.
2. `subtotal = Σ line_amount`.
3. Allocate the invoice discount `D` across the lines in proportion to `line_amount`:
   - `raw_i = D × line_amount_i / subtotal`.
   - `allocated_i = floor(raw_i)` at currency scale.
   - Distribute the remaining `D − Σ allocated_i` one currency unit at a time to lines ordered by largest fractional remainder, ties broken by ascending `line_number`.
   - Result: `Σ allocated_i = D` exactly.
4. `taxable_amount_i = line_amount_i − allocated_i`.
5. `tax_amount_i = round(taxable_amount_i × tax_rate_i / 100)`.
6. `line_total_i = taxable_amount_i + tax_amount_i`.
7. Invoice `discount_amount = D`, `tax_amount = Σ tax_amount_i`, `grand_total = subtotal − D + tax_amount = Σ line_total_i`.

Invoice-level tax must never be recomputed independently from the invoice-level taxable amount; it is always the sum of rounded line taxes.

If `subtotal = 0`, the discount must be 0 (BR-CAL-004) and no allocation occurs.

### BR-CAL-013 — Monetary Input Precision

Monetary inputs (unit prices, discount amounts, payment amounts) must not have more decimal places than the currency scale (0 for VND). Requests that do must be rejected with HTTP 400 rather than silently rounded.

Monetary values in API payloads must be parsed directly into BigDecimal.

### BR-CAL-011 — Example Calculation

Assume all items use the same illustrative tax rate.

| Component | Amount |
| --- | ---: |
| Subtotal | 1,000,000 VND |
| Discount | 100,000 VND |
| Taxable Amount | 900,000 VND |
| Example Tax (10%) | 90,000 VND |
| Grand Total | 990,000 VND |

Expected result:

990,000 VND

The example tax rate is for calculation testing only.

## 8. Invoice Lifecycle Rules

The invoice lifecycle and payment status must be stored separately.

### 8.1 Invoice Status

Supported invoice lifecycle states:

- DRAFT
- ISSUED
- CANCELLED

### 8.2 Payment Status

Supported payment states:

- UNPAID
- PARTIALLY_PAID
- PAID

An invoice may therefore be ISSUED and PARTIALLY_PAID at the same time.

Overdue status should be derived from the due date and outstanding balance, rather than treated as the primary invoice lifecycle state.

### BR-INV-009 — Allowed State Transitions

| Current Status | Action | New Status |
| --- | --- | --- |
| DRAFT | Edit | DRAFT |
| DRAFT | Issue | ISSUED |
| DRAFT | Cancel | CANCELLED |
| ISSUED | Record payment | ISSUED |
| ISSUED | Generate PDF | ISSUED |
| ISSUED | Send email | ISSUED |

The payment status is updated independently when payments are recorded.

Cancellation of an issued invoice must use a separately defined correction or cancellation workflow appropriate to the document type.

The initial MVP must not implement arbitrary cancellation of issued financial records.

### BR-INV-010 — Draft Modification

Draft invoices may be modified by authorized users.

The system must recalculate totals after relevant changes.

A draft update must leave at least one item (consistent with US-06 AC-03).

Only DRAFT invoices may be modified.

### BR-INV-011 — Issued Invoice Immutability

Issued invoices must not allow direct modification of finalized financial information.

Changes requiring financial correction must use a dedicated correction workflow in a later phase.

### BR-INV-012 — Cancelled Draft

A cancelled draft must not be issued.

Cancelled drafts may remain stored for traceability.

## 9. Invoice Issuance Rules

### BR-ISS-001 — Issuance Validation

Before issuing an invoice, the system must validate:

- Customer exists.
- Invoice contains at least one valid item.
- All quantities are valid.
- Financial calculations are valid.
- Due date is valid.
- Invoice remains in DRAFT status.

### BR-ISS-002 — Unique Invoice Number

Each issued invoice must receive a unique invoice number within the defined numbering scope.

Example:

INV-2026-000001

INV-2026-000002

INV-2026-000003

The numbering format must be configurable.

A database unique constraint must enforce uniqueness.

### BR-ISS-003 — Concurrent Issuance

If multiple requests attempt to issue the same invoice simultaneously, only one issuance operation may succeed.

The system must prevent duplicate invoice numbers and duplicate finalization.

The implementation may use:

- Database transactions.
- Optimistic locking.
- Unique constraints.
- Idempotency keys.

### BR-ISS-004 — Idempotent Issuance

Repeating the same successful issuance request must not produce a new invoice number.

API contract:

- A request that repeats a previously successful issuance with the same `Idempotency-Key` returns the stored original response.
- Any other issuance request for an invoice that is not in DRAFT status returns HTTP 409 with error code `INVOICE_NOT_DRAFT`.

The `Idempotency-Key` header is optional for issuance because the DRAFT → ISSUED transition itself cannot occur twice.

### BR-ISS-005 — Historical Snapshot

When an invoice is issued, the system must preserve:

- Customer billing information.
- Business information.
- Product descriptions.
- Unit prices.
- Quantities.
- Discounts.
- Tax rates.
- Final calculated amounts.

### BR-ISS-006 — Transaction Boundary

Invoice issuance and the related database changes must be committed atomically.

External operations such as SMTP delivery must not occur inside the issuance database transaction.

Issuance must lock the invoice row (`SELECT … FOR UPDATE`) before validating its DRAFT status, and must allocate the invoice number from `invoice_sequences` inside the same transaction so that a rollback does not consume a number.

## 10. Payment Management Rules

### BR-PAY-001 — Valid Invoice

A payment must reference an existing issued invoice.

Payments must not be recorded against draft invoices.

### BR-PAY-002 — Valid Payment Amount

Payment amount must be greater than zero.

Negative or zero-value payments must be rejected.

### BR-PAY-003 — Outstanding Balance

Outstanding Balance = Grand Total - Sum of Valid Payments

A valid payment is a payment record with record status COMPLETED.

The outstanding balance must not be negative.

### BR-PAY-004 — Partial Payment

If:

0 < Total Paid < Grand Total

Then:

Payment Status = PARTIALLY_PAID

### BR-PAY-005 — Full Payment

If:

Total Paid = Grand Total

Then:

Payment Status = PAID

### BR-PAY-006 — Unpaid Invoice

If:

Total Paid = 0

Then:

Payment Status = UNPAID

### BR-PAY-007 — Overpayment Prevention

A payment must not exceed the outstanding balance.

An overpayment request must be rejected.

### BR-PAY-008 — Duplicate Payment Prevention

Payment requests must include an `Idempotency-Key` header. A request without it is rejected with HTTP 400.

Retrying the same request must not create duplicate payment records.

Reusing a key with a different request payload must be rejected with HTTP 409 (`IDEMPOTENCY_KEY_REUSED`).

### BR-PAY-009 — Concurrent Payments

Concurrent payment operations must not create an invalid outstanding balance.

The backend must lock the invoice row (`SELECT … FOR UPDATE`) before reading the outstanding balance, then insert the payment and update the invoice payment summary in the same transaction.

Database check constraints (`paid_amount <= grand_total`, `balance_due = grand_total - paid_amount`) act as the final safeguard.

### BR-PAY-010 — Payment Auditability

Payment records must include:

- Invoice reference.
- Payment amount.
- Payment method.
- Payment timestamp.
- User responsible for recording the payment.
- Optional external payment reference.

Payment records must remain traceable.

## 11. PDF Generation Rules

### BR-PDF-001 — Eligible Invoice

Final invoice PDFs may only be generated from issued invoices.

Draft previews, if implemented, must be clearly distinguished from issued documents.

### BR-PDF-002 — Required PDF Content

The generated PDF must include:

- Business information.
- Customer billing information.
- Invoice number.
- Issue date.
- Due date.
- Invoice items.
- Quantities.
- Unit prices.
- Discounts.
- Applicable taxes.
- Grand total.

### BR-PDF-003 — Historical Accuracy

PDF generation must use the stored issued invoice snapshot.

It must not rely on current customer or product values.

### BR-PDF-004 — Character Support

PDF generation must correctly support Vietnamese characters.

Fonts used by the PDF engine must support the required Unicode characters.

### BR-PDF-005 — Document Consistency

Regenerating an invoice PDF must preserve the same issued financial information.

Presentation changes must not alter finalized financial values.

## 12. Email Delivery Rules

### BR-EMAIL-001 — Valid Recipient

An invoice email must have a valid recipient address.

Invalid addresses must be rejected before delivery.

### BR-EMAIL-002 — Issued Invoice Requirement

Only issued invoices may be sent as final invoice documents.

### BR-EMAIL-003 — Asynchronous Delivery

Email delivery must be separated from the invoice issuance transaction.

A delivery job should be created and processed independently.

### BR-EMAIL-004 — Delivery Status

Email jobs must support the following statuses:

- PENDING
- PROCESSING
- SENT
- FAILED

Status semantics:

- PENDING — waiting to be processed. This includes jobs that failed with a retryable error and have attempts remaining; `next_attempt_at` is then set in the future.
- PROCESSING — claimed by a worker until `locked_until`. A job whose lock has expired is eligible to be claimed again.
- SENT — the provider accepted the message. This is a terminal status.
- FAILED — a permanent error occurred or `max_attempts` was reached. This is a terminal status; a manual resend creates a new request.

### BR-EMAIL-005 — Retry Policy

Failed email deliveries may be retried.

The retry count must be limited.

A suggested initial policy is three attempts with increasing retry delays.

### BR-EMAIL-006 — Duplicate Job Prevention

The same idempotent delivery request must not create duplicate jobs.

Manual send requests must include an `Idempotency-Key` header. System-generated jobs (for example, reminders) use a deterministic key such as `REMINDER:{invoiceId}:{reminderPeriod}`.

### BR-EMAIL-007 — Delivery Failure Independence

An SMTP failure must not roll back an already committed invoice issuance.

### BR-EMAIL-008 — Delivery Interpretation

SENT indicates that the configured email provider accepted the message.

It must not be interpreted as proof that the recipient opened or read the email.

## 13. Automation Rules

### BR-AUTO-001 — Overdue Detection

An invoice is overdue when:

- Invoice status is ISSUED.
- Outstanding balance is greater than zero.
- Due date is earlier than the current business date.

### BR-AUTO-002 — Reminder Eligibility

Only eligible overdue invoices may receive payment reminders.

Fully paid invoices must not receive overdue payment reminders.

### BR-AUTO-003 — Duplicate Reminder Prevention

The system must avoid creating duplicate reminder jobs for the same invoice and reminder period.

### BR-AUTO-004 — Scheduled Execution

Scheduled tasks must be designed to support safe repeated execution.

Running the same job more than once must not create duplicate invoices or duplicate payment records.

### BR-AUTO-005 — Failure Logging

Background job failures must be recorded.

Failed operations must be identifiable for investigation and retry.

## 14. Data Integrity Rules

### BR-DATA-001 — Relational Integrity

Database foreign keys must enforce valid relationships between entities.

### BR-DATA-002 — Financial Constraints

Financial columns must use appropriate precision and scale.

Database constraints must prevent invalid negative values where prohibited.

### BR-DATA-003 — Transaction Management

Operations involving multiple related database changes must be transactional.

Spring transaction management should be applied at the service layer.

### BR-DATA-004 — Historical Preservation

Issued invoice records and their financial snapshots must be preserved.

Changes to customer and product catalogues must not rewrite historical financial information.

### BR-DATA-005 — Database Migrations

Database schema changes must be versioned using Flyway.

Manual production schema changes should not be used as the normal deployment process.

### BR-DATA-006 — Optimistic Locking

Entities subject to conflicting concurrent updates should support version-based concurrency control.

Invoice entities should contain an appropriate version field.

### BR-DATA-007 — Time Handling

System timestamps must use a consistent time standard.

UTC should be used for persisted event timestamps.

Business dates and scheduled operations must use the configured business timezone.

## 15. Audit Logging Rules

### BR-AUDIT-001 — Important Operations

The system must record important business events, including the following. Recording issuance and payment events is part of the MVP. The audit query API (US-13) is P1.

- Invoice issuance.
- Payment creation.
- Invoice cancellation.
- Important customer changes.
- Important product changes.
- Permission changes.

### BR-AUDIT-002 — Audit Information

Audit records should contain:

- Actor identifier.
- Action.
- Entity type.
- Entity identifier.
- Timestamp.
- Relevant change information.

### BR-AUDIT-003 — Sensitive Information

Passwords, tokens, secrets, and sensitive authentication information must not be written to audit logs.

### BR-AUDIT-004 — Audit Integrity

Audit records must not be freely editable through ordinary business APIs.

## 16. Error Handling Rules

### BR-ERR-001 — Standardized API Response

Business errors must return a consistent response structure.

Example:

```json
{
  "timestamp": "2026-09-28T10:00:00Z",
  "status": 400,
  "errorCode": "INVALID_INVOICE_QUANTITY",
  "message": "Invoice item quantity must be greater than zero",
  "path": "/api/v1/invoices"
}
```

### BR-ERR-002 — Validation Errors

Invalid request data must return HTTP 400.

### BR-ERR-003 — Authentication Errors

Missing or invalid credentials must return HTTP 401.

### BR-ERR-004 — Authorization Errors

Insufficient permissions must return HTTP 403.

### BR-ERR-005 — Missing Resources

Nonexistent resources must return HTTP 404.

### BR-ERR-006 — Business Conflicts

Conflicting operations must return HTTP 409 where appropriate.

Examples:

- Duplicate invoice issuance (`INVOICE_NOT_DRAFT`).
- Invalid invoice state transition.
- Idempotency key reused with a different payload (`IDEMPOTENCY_KEY_REUSED`).
- Duplicate SKU.
- Concurrent modification.

### BR-ERR-007 — Internal Errors

Unexpected internal errors must return HTTP 500 without exposing internal stack traces to clients.

Business rule implementation is considered complete when:

- The rule is implemented in the appropriate service.
- Input validation is enforced.
- Relevant database constraints are implemented.
- Expected errors are handled consistently.
- Unit tests pass.
- Integration tests pass where required.
- Concurrency behavior is tested where relevant.
- API documentation is updated.

## 22. Regulatory and Scope Boundary

Smart Invoice initially generates commercial invoice documents and PDF billing records.

PDF generation alone does not establish that a document is a legally compliant electronic tax invoice.

Official electronic tax-invoice processing, digital signatures, tax authority integration, and regulatory document formats are outside the initial MVP.

Any future regulated invoice functionality must be implemented as a separately specified integration and verified against the applicable requirements.
